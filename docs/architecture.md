- **Classification & Data Quality (Phase 5):** Deterministic, metadata-only classification proposals (versioned rules, confidence semantics, immutable history with input fingerprints); on-demand data-quality checks (missing metadata, invalid/unsupported extensions, conflicts, duplicate candidates, stale observations, source-mapping inconsistencies, unclassified) — never reads file contents, never mutates asset fields, never selects/executed a retention policy or lifecycle action. Classification writes require `classification:write` plus institution scope under the Phase 7 authorization boundary (ADR-0014); in production the auth layer fails closed rather than relying on the older blanket write guard (ADR-0010–0012). Frontend minimal view with loading/empty/error states and explainable evidence/warnings/conflicts.
- **Unified Review Workflow & Governance (Phase 6):** A single review queue (`GET /api/v1/retention/recommendations`) with server-side institution/review-status/recommendation/severity filters, permitted-metadata search, deterministic urgency/age sorting, and pagination; a read-only unified asset view (`GET /api/v1/governance/assets/{asset_id}`) aggregating inventory + source/scan, latest classification, quality findings, applicable policy and exact version, latest assessment and history, active holds, and append-only decisions with explicit provenance labels. Human decisions reuse the append-only `retention_decisions` table (`retain` / `request_more_information` / `approve_for_later_workflow` / `reject`), now race-safe via a unique `assessment_id` constraint (ADR-0013). Submissions carry optimistic-concurrency tokens and are rejected as stale (`409 stale_review_conflict`) or hold-blocked (`409 hold_conflict`); decisions are not execution commands and no archive/restore/move/delete is implemented.
- **Authorization on writes:** Every write route requires the appropriate permission plus institution scope (Phase 7, ADR-0014); out-of-scope writes receive the same 404 as missing resources and are audited. The older blanket production 503 guards (ADR-0010–0013) are historical and are not the current authorization boundary. Read-only operations remain available.
- **Identity, Authorization & Decision Supersession (Phase 7):** Server-verified identity via strict HS256 JWT bearer tokens (stdlib only) with issuer/audience/expiry/signature validation; production fails closed (503 `auth_not_configured:`) whenever the signing secret is missing or is the development placeholder, and the development sign-in provider is hard-disabled there (ADR-0014). Authorization is one `require_permission` dependency on every protected endpoint, backed by a local user directory that is authoritative over token claims; roles are viewer/reviewer/admin plus a platform administrator flag, out-of-scope resources answer 404 (no existence leak), and denied writes — permission failures and write scope failures — are audited (`authorization.denied`); scope-denial payloads deliberately omit the target institution id. Human decisions gain **supersession** (ADR-0015): a correction is a new decision linked by `supersedes_decision_id` (unique successor index, lineage/self-reference/cycle validated, effective decision derived server-side, full history preserved - no edit or delete path exists anywhere). The frontend adds sign-in/sign-out, permission-aware navigation and actions, institution scope selection, session-expired handling, and supersession/effective markers in the review history - all usability only; the backend re-authorizes every request. Migration `0011_platform_admin_default_false` corrects the unsafe `0008` platform-admin server default: it revokes ambiguous existing grants and sets future defaults to false (ADR-0017); a trusted operator must explicitly re-grant verified platform admins. Migration `0012_audit_platform_admin_reset` records the post-reset state in the append-only audit trail without changing access; it is forward-only evidence and cannot reconstruct revoked identities, so the pre-migration export remains mandatory. A read-only preflight (`scripts/migration_preflight.py`) reports the credential-free target and revision state before an operator applies migrations to an existing database, rejects non-MySQL dialects, and keeps backups and platform-admin re-grants as explicit human gates (ADR-0018). Migration `0010` repairs the `classification_results` downgrade inversion and sets the supported rollback boundary at `0005` with tested safe failure below it (ADR-0016). A real identity provider (RS256/JWKS) is **not** configured or claimed: production authentication stays fail-closed until an operator sets a real secret and IdP integration is implemented and tested.
- **Deployment Hardening (Phase 9):** A GitHub Actions workflow (`.github/workflows/ci.yml`, ADR-0019) is configured to run on pull requests and pushes to `main` on Linux (it has not yet executed on GitHub): backend and operator-script Ruff, backend tests, the 19-test live MySQL migration suite against an ephemeral `mysql:8.4` service, and the frontend typecheck/tests/production build, with no repository secret. The MySQL step fails when `MIGRATION_TEST_DB_URL` is absent and asserts that all 19 tests pass rather than skipped. GitHub Actions are pinned to full commit SHAs and the MySQL image to a verified digest. The local Windows PowerShell gate also lints the operator scripts and restores the caller's directory on failure. `docs/backup-restore.md` documents a verified restore drill on a disposable MySQL instance (21/21 table checksums, revision `0011` at drill time; current head `0012`, scratch database only), and `docs/production-readiness.md` records the unresolved production blockers (RS256/JWKS identity provider, secret management, TLS/reverse-proxy trust, database least privilege, audit/monitoring, backup automation, supply chain). No deployment, production connection, real identity provider, or durable-database migration was performed.
- **Azure Preparation (Phase 10, ADR-0021 — infrastructure and repository structure only; nothing deployed):** `infra/azure/` holds a resource-group-scoped Bicep entry point, seven modules (network, key vault, MySQL Flexible Server, App Service Linux backend, Static Web Apps frontend, monitoring, reusable private link) and dev/prod parameter files, with every name, region, tier, network mode and secret *name* parameterised and no subscription, tenant, hostname or price asserted. The vault is created empty; `DATABASE_URL` and `AUTH_JWT_SECRET` reach the runtime as App Service Key Vault references resolved by a user-assigned managed identity granted only Key Vault Secrets User; the single deploy-time secret is `@secure()` and referenced from an operator-owned bootstrap vault. Application Insights is off unless an existing Log Analytics workspace is named, and App Service VNet integration is deliberately not templated — so the private MySQL/vault paths are documented as unreachable until an operator adds it. `.github/workflows/azure-deploy.yml` (added separately from `ci.yml`, which is untouched) triggers only on `workflow_dispatch`, uses GitHub OIDC with no repository secret, separates build from deploy, gates production behind a protected environment, runs only read-only smoke checks, and never runs Alembic. The one application change is a real startup defect the audit exposed: pydantic-settings JSON-decodes `list[str]` settings in the env/dotenv source before validators, so the comma form `.env.example` shipped raised `SettingsError`, which makes any flat-string application setting (i.e. every deployed platform) fail to start — now `Annotated[list[str], NoDecode]` with a validator accepting both comma and JSON forms, `pydantic-settings>=2.7`, plus six tests. Production authentication remains fail-closed and HS256-only; no OIDC claim is made. **The templates were never compiled, linted, or what-if validated** (`az`/`bicep`/`node` unavailable, Bicep download unreachable), the frontend typecheck/Vitest/build did not run here, and `docs/azure-architecture.md` carries the gap analysis, blocker list and implemented-vs-templated-vs-unverified split, with `docs/azure-deployment.md` and `docs/azure-cutover-checklist.md` as the runbook and gate.
- **Frontend Redesign, Tokens & Data-Fetching Correctness (redesign Phase 1–2, ADR-0022 — presentation and request lifecycle only; no capability added):** `frontend/src/index.css` is now a Tailwind v4 `@theme` sheet of 75 semantic tokens (surfaces, borders, ink tiers, accent, state colors, typography scale, radius, spacing) and `frontend/src/lib/semantic.ts` is the single tone/label resolver (`resolveTone`, the state tables, `statusLabel`) with `lib/labels.ts` retained as a compatibility shim, so existing components kept their APIs, visible copy, routes and layouts. Every read in `frontend/src/api` gained an optional trailing `AbortSignal` threaded into `apiGet` — transport-only plumbing that never changes a URL, method, payload or response contract — and all 16 `useApiQuery` call sites moved to the dependency-declared `useApiQuery(fetcher, deps)` contract: an explicit type-tagged dependency signature (so `null` and `""` never collide) folded with a `refetch` token drives one effect, the latest fetcher is read from a ref (no stale closures, no lint suppressions — the project has no ESLint to suppress), each run owns an `AbortController` plus an `active` flag that cancels the previous request and blocks a stale or post-unmount write, errors clear data, and previous data stays visible during a reload. The recommendations queue's `firstRender` ref workaround is gone; search text is debounced 300 ms and joined with the same server-side filter/sort/pagination semantics. `assessAsset` is a POST and deliberately ignores the signal — cancelling the client's view of an accepted mutation would not undo the server-side record — and the assessment runner now mounts only for roles holding `retention:assess`, so an unauthorized viewer sees an explicit "your role cannot run assessments" state and issues no POST; the existing `AssetGovernance` gate is unchanged, the backend re-authorizes every request, and no assessment result is fabricated. Verified locally under portable Node 24 through `scripts/check.ps1` (all six gates, exit 0): backend Ruff, operator-script Ruff, pytest 222 passed / 20 skipped, frontend typecheck, Vitest 139 tests at that checkpoint (18 dedicated to the hook's dependency/cancellation behaviour, plus page-level request-lifecycle and permission-gate regressions) and the production build. The flows were not exercised against a live backend in this environment.
- **Frontend Redesign, Design System (redesign Phase 3, ADR-0023 — shared layer only; no page redesigned):** `frontend/src/components/ui/` gains a framework-free primitive layer — `Button`, `IconButton`, `Input`, `Select`, `Textarea`, `Field`, the `Table` family, `Dialog`, `Tabs`, `Toast`/`ToastProvider`/`useToast` and `Progress` — written against the `@theme` tokens, with a hand-rolled focus trap and focus restore in `Dialog`, roving arrow-key/Home/End activation in `Tabs`, an always-mounted `aria-live="polite"` notification region, `role="progressbar"` semantics (and no invented value when indeterminate), and a `Field` that generates the label/hint/error id associations a control needs. Status meaning stays in `lib/semantic.ts` and status *appearance* is now defined once per medium: `ui/statusClasses.ts` (`TONE_SURFACE`, `TONE_SOLID`) and `STATUS_GLYPHS` in `components/icons.tsx`, keyed by the new `StatusTone`, with `resolveStatusTone` folding the brand `accent` onto `neutral` so a state is never painted as a brand colour; `Badge`, `BarList`, `Progress` and `Toast` read those tables instead of carrying copies. `index.css` adds focus/on-accent/disabled/overlay roles, control-row spacing, overlay radius and shadows, two named animations, a base `:focus-visible` outline and a `prefers-reduced-motion` guard, and typography is genuinely self-hosted: Inter 400/500/600/700 latin `woff2` (pinned `@fontsource/inter@5.3.0`, SIL OFL text included) under `src/assets/fonts/` with `@font-face` + `unicode-range` + `font-display: swap`, so the built CSS fetches only same-origin font assets. `ToastProvider` is mounted above the router in `App.tsx` (a provider element only — routes, layout, permission gates and API contracts untouched, and no page calls `useToast()` yet); existing components keep their APIs and pages keep their own markup, so raw palette classes still exist per page until each route's phase. Verified through `scripts/check.ps1` under portable Node 24 — exit 0, "All checks passed": backend Ruff, operator-script Ruff, pytest 222 passed / 20 skipped, typecheck exit 0, Vitest 213/213 passed (74 new design-system tests), production build exit 0 (CSS 37.96 kB / gzip 8.17 kB, JS 374.28 kB / gzip 109.31 kB, four `woff2` assets emitted); a dev-server browser check confirmed the four weights loading, the live region present and no console error from the new code, with the sign-in screen's honest API-unavailable state unchanged.
